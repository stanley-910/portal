## Selection and boundaries

Use the existing Duffel integration and add LiteAPI as an optional second hotel source for Hong Kong, Shanghai, Seoul and Tokyo and any other coordinate search. API searches must share the app's 8-second outer budget; no provider may invent availability. Hostels retain estimates until dedicated source access is established. Do not classify properties by a word in the name.

LiteAPI requires actual guest nationality. Use an explicitly supplied country code (the hotel's country and deployment location are not substitutes). Missing nationality means no LiteAPI request. Never expose sandbox rates as live. Keep real rate source and quote dates in results. Do not turn a LiteAPI quote into a Booking.com booking link: that would imply the other seller honours it and conflict with third-party-mapping restrictions.

Only complete offers for all requested rooms with validated currency and public display price are eligible. Exclude offers with extra pay-at-property charges until the UI can display them. Public suggested selling prices are required where supplied; do not expose net prices as public deals. Hotel star ratings are separate from guest-review scores.

## Implementation and verification

- `searchAvailableHotels` runs Duffel and LiteAPI within a shared 8-second signal and ranks the first available source (Duffel preferred). Missing key/nationality, empty, rejected, sandbox or failed rates fall back to LiteAPI's listings (real hotels and photos, typical prices marked estimated), then to the estimated catalog. A production LiteAPI key needs a registered business; the sandbox key reads the same real hotel content (checked 2026-10-04 for Tokyo: real names, stars, coordinates and `main_photo`), only its rates are fake.
- LiteAPI makes a bounded six-hotel coordinate/rate request and parallel detail requests under the same signal. It validates official detail IDs, real coordinates, hotel classification and star rating; it validates every room occupancy, currency and complete offer sum, applies public SSP floors, and drops extra local-charge offers.
- Nationality is an optional explicit hotel-panel selector. No destination/account inference, signup, or login gate. Source, quoted dates and party appear beside live results; no live quote is advertised as a Booking.com booking.
- Offline fixture is **synthetic, documentation-shaped**, assembled from the public rate-structure and hotel-detail examples, with fictional IDs and amounts. It is not a recorded production response. Live account/inventory smoke verification remains blocked on an owner-provided API key. `scripts/stays-smoke.mts` checks all four demo cities through the running app without creating bookings.

Validation: `pnpm test --maxWorkers=2` passed 711 tests (72 files, 1 skipped) before the final two guard/deadline tests; the final targeted hotel suite passed all 29 tests. Plain `pnpm test` encountered an unrelated 5-second globe engine test timeout during concurrent agent test execution. `pnpm lint` passed with the existing LogoReveal unused-expression warning; targeted lint passed. `pnpm exec tsc --noEmit` reached only missing generated Next `LayoutProps` / `PageProps` globals in the fresh worktree, not errors in changed files. Final integrated checks remain the coordinator's responsibility.

## Review fixes and app verification

Hotel UI results are keyed to the whole query so changed nationality, dates or occupants immediately hide earlier
quotes. Saved nightly budgets are always planning estimates until the storage model can preserve quote scope.
Known transport arrival dates drive hotel check-in; no night before an overnight arrival is charged in the shared split.
The four-city app smoke with current credentials returned only estimates, confirming fallback rather than live access.
A real browser run rendered the hotel panel and optional nationality selector without page errors.

Browser regression: changing nationality with the next request deliberately delayed immediately removed all earlier selectable rows; no page errors.
